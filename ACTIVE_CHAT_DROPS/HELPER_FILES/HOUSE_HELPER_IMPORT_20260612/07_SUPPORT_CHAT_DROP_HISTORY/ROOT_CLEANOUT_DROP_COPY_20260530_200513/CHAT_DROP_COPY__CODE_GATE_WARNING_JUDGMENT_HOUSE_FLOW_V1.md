### Mirror Water

A warning is a mirror. It shows contact with a risk surface.

It can mean:
- expected report writing;
- noisy but harmless pattern shape;
- a repeated assistant generation problem;
- a custody/move/delete risk;
- a repo/save risk;

### Quick Signal

Every warning needs a fast label:

EXPECTED_ALLOWED  
EXPECTED_BUT_NOISY  
INVESTIGATE  
BLOCKER_ADJACENT  
EXPLICIT_ALLOW_REQUIRED  
UNKNOWN_REVIEW

### Sweet Fit

Warnings must be judged against the script’s job.

A read/report helper that writes a report should warn but usually continue.

A save helper touching Git can continue only inside an explicit save lane with proof.

A delete/move/network/system helper should not continue unless that exact risk is the locked object and explicitly allowed.

### Red Blade

Hard block or stop-review surfaces:
- delete/remove;
- move/rename/custody change;
- Git commit/push/staging without save lane;
- network/web requests;
- registry/services/scheduled tasks;
- Defender/security changes;
- admin/system changes;
- broad root scans beyond approved bounds;
- obfuscated execution;
- downloaded execution without Code Gate.

### Big Sky

Warnings become learning only when repeated.

One warning: WATCH.  
Two similar warnings: LIKELY PATTERN.  
Three or more: CONSOLIDATION CANDIDATE or Code Gate UX improvement candidate.

## Warning Judgment Flow

`warning -> script class -> intended behavior -> risk surface -> expected? -> repeat count -> action -> ledger -> possible rule/tool upgrade`

Expanded:

1. Capture the warning title.
2. Capture reason and evidence.
3. Identify target helper.
4. Identify script class.
5. Compare warning to declared job.
6. If expected, mark EXPECTED_ALLOWED.
7. If expected but noisy, mark EXPECTED_BUT_NOISY.
8. If risky, mark INVESTIGATE or EXPLICIT_ALLOW_REQUIRED.
9. If blockers or failed run are present, mark BLOCKER_ADJACENT.
10. Count repeats.
11. Decide action.
12. Add to evidence ledger.
13. If repeated enough, promote to improvement candidate.

## Script Classes

### READ_ONLY_REPORT

Allowed:
- parser pass;
- bounded file reads;
- report writing to known report lane;
- local receipt/report output.

Warnings usually acceptable:
- local file write command when report writing is declared.

Escalate:
- Git, delete, move, network, system changes.

### LOCAL_FILE_CREATION

Allowed only when file creation is the task.

Needs:
- output path;
- receipt or clear console output;
- no hidden root slop;
- exact destination.

### REPO_SAVE

Needs:
- user intent to save;
- repo path;
- clean pre-status;
- exact staged file list;
- commit;
- push if not local-only;
- final clean status;
- receipt.

Warnings:
- Git warning may be expected only in this lane.
- Still needs proof.

### MOVE_RENAME_CLEANUP

Needs:
- explicit custody object;
- source path;
- destination path;
- hash before/after when practical;
- no delete;
- receipt.

Warnings:
- move/rename warning is not casual; it is custody-sensitive.

### DELETE

Default blocked unless user explicitly approves the exact deletion.

### NETWORK

Default blocked unless the locked object is network work and permission is explicit.

### SYSTEM_CHANGE

Default blocked.

Includes:
- registry;
- services;
- scheduled tasks;
- Defender/security settings;
- admin-level machine changes.

## Warning Classes

### EXPECTED_ALLOWED_REPORT_WRITE

Meaning:
The helper writes reports/receipts as its declared job.

Continue when:
- parser passed;
- target path is known;
- output lane fits;
- no other risk surfaces are present.

Do not worry too much.

### EXPECTED_BUT_NOISY_PATTERN_SHAPE

Meaning:
The warning reflects a style or shape that is not dangerous, but repeated enough to improve generation rules.

Continue when harmless.

Use as evidence for:
- cleaner helper style;
- less confusing reports;
- less repeated warning noise.

### WATCH_LEDGER_ONLY

Meaning:
Not dangerous yet, but should be counted.

Continue when the warning is understood.

### INVESTIGATE_CUSTODY_SURFACE

Meaning:
Move/rename/copy/write path surfaces may affect custody.

Stop or slow down unless this is the locked cleanup object.

### INVESTIGATE_NETWORK_SURFACE

Meaning:
Script may contact outside systems.

Stop unless explicitly approved.

### INVESTIGATE_SYSTEM_CHANGE_SURFACE

Meaning:
Script may alter machine state.

Stop unless explicitly approved.

### REQUIRES_EXPLICIT_SAVE_OR_REPO_PERMISSION

Meaning:
Git/save behavior is present.

Continue only in save lane.

### BLOCKER_ADJACENT_REVIEW

Meaning:
Warnings appear near blockers, target failure, or run failure.

Do not dismiss.

### UNCLASSIFIED_REVIEW

Meaning:
The warning is not known yet.

Manual review required.

## How to “feel” growth

A clean system should not only obey a rule. It should sense pressure.

Use this map:

- Light touch: expected report writing.
- Grit: noisy pattern repeated.
- Heat: custody/repo/network/system warning.
- Smoke: warning plus blocker or failed target.
- Echo: same warning repeated across runs.
- Signal: repeated warning with a clear fix.
- Growth point: signal becomes a policy, helper improvement, or future node.

This is not mystical by itself. It is operational feeling:
pressure -> classification -> memory -> behavior change.
